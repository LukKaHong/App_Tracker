# 【问题反馈】ML307C-DC OpenCPU SDK：MQTT 断开/重连周期泄漏 rti 线程表项，73 次后溢出 Silent Reset

- **芯片/模组**：ML307C-DC-CN
- **SDK 版本**：OpenCPU Standard 1.0.4（CD_ML307C-DC-CN_OpenCPU_Standard_1.0.4.2605181713_release）
- **测试固件 build**：Sep 10 2026 16:36:10
- **问题类型**：SDK 内部资源泄漏（rti 线程数组溢出）→ Silent Reset
- **可复现性**：100%（受控实验 6/6 次复现，外加现场场景多台设备反复发生，崩点计数零偏差）

---

## 1. 现象

设备周期性执行 MQTT 断开→重连（约 6.5 秒一个周期），**精确在第 73 次断开时**设备静默复位。串口输出：

```
[2026-09-10 16:45:07] MQTT-LEAK-TEST [73/120] disconnect
[CMMQTT] send len:2
[CMMQTT] id:0, msg type:3
mqtt connack fail:2 (was_connected=1)
mqtt disconnected
[ELOOP] unregister event=0x7e044c60
[ELOOP] unregister event=0x7e044be8
[ELOOP] unregister event=0x7e044c00
[ELOOP] unregister event=0x7e044c18
asocket_cb 3 11 / asocket not found ×3
[CMMQTT] id:0,disconnect from server
EE LOG: LR: 0x80173d47, PC: 0x8016d58c, SP: 0x7e0bac98
EE LOG: DESC: rti thread array overflow, cnt 0x5c, FILE: utilities.c, LINE: 694
EE LOG: Task: pet_main
EE LOG: Send Plp Mem Dump CMD
EE LOG: Silent Reset
```

崩溃后设备重启，测试自动从头开始，约 8 分钟后再次在同一轮次崩溃——形成稳定的崩溃循环（本次日志捕获 6 个完整循环，**6 次全部死在第 73 轮 disconnect，EE LOG 签名完全一致**）。

## 2. 复现步骤

1. 开机，等待网络注册（CEREG=1）
2. 创建 MQTT client（`cm_mqtt_client_create` + `cm_mqtt_client_set_opt` 配置回调/keepalive 120s/QoS1，`cm_mqtt_client_connect` 连接 119.23.217.155:18883），连接成功并完成订阅
3. 循环执行 120 次：
   - `cm_mqtt_client_disconnect()` → 等待 200ms
   - 等 3 秒
   - `cm_mqtt_client_connect()`（**复用同一 client 对象，不销毁不重建**）→ 等连接成功
   - 等 2 秒
4. 第 73 次 disconnect 过程中触发上述 EE LOG 复位

测试代码见附件 3、附件 4。测试期间 **WiFi 扫描全程未运行**，已排除 cm_wifiscan 参与。

## 3. 关键定位证据

### 3.1 泄漏速率为每周期恰好 1 条（线性、无偏差）

EE LOG 中 cnt=0x5c=92（rti 数组容量上限）。开机后基线约 19 条 + 73 周期 × 1 条/周期 = 92，恰好溢出。6 次复现均精确死在第 73 轮，计数零偏差，说明是**确定性资源泄漏**而非偶发稳定性问题。

### 3.2 已排除 cm_mqtt_client_destroy

我们做了对照实验：

| 固件 | client 生命周期管理 | 崩溃轮次 | EE LOG |
|------|-------------------|---------|--------|
| A（前一日） | 每周期 create/destroy | 第 73 轮 | 同签名 cnt=0x5c |
| B（本日志，build 16:36:10） | 一次创建终身复用，**全程零 destroy 调用**（日志中无任何 destroy client 打印可证） | 第 73 轮 | 同签名 cnt=0x5c |

两版崩点完全相同 → destroy 不泄漏，**泄漏发生在 connect/disconnect 周期内部的 SDK 路径**（候选：ADNS 异步解析、asocket、MQTT 内部状态机/线程的 rti 表项登记与回收逻辑）。

### 3.3 每轮重连的 SDK 行为痕迹（供贵司定位参考）

每轮 reconnect 序列均可见（即使主机名为 IP 字面量直连）：

```
[ADNS] cm_async_dns_request cid = 1
[CMMQTT] is_ipv4
[ELOOP] register_event / unregister event（4 个事件地址每轮相同：0x7e044be8/c00/c18/c60）
asocket open ok 0 3            ← fd=3 每轮复用
ipv4: 1 10.108.49.54
[CMMQTT] conn ret:0
```

- eloop 事件内存地址每轮相同（堆上复用，无内存泄漏迹象）
- asocket fd=3 每轮复用（无 fd 泄漏）
- virt_at 队列/任务每轮打印 already exist（复用，无泄漏）
- 唯一线性累积的只有 rti 线程表项计数（CNT 从 1 递增至溢出）

### 3.4 一处待贵司解释的现象

EE LOG 的 `Task: pet_main` 是我们的主任务，而断开的调用方是测试任务（mqtt_leak）。溢出发生时正在执行 rti 登记动作的上下文与断开发起方不一致，推测登记发生在 SDK 内部异步完成路径或主任务上下文的某个 SDK 调用中——具体登记点（utilities.c:694 的调用者）请贵司结合符号定位。

## 4. 产品背景与业务影响

产品为宠物追踪器（ML307C-DC + OpenCPU）。每个定位周期需要执行一次 WiFi 扫描做辅助定位，扫描要求 modem 静默窗口（等待 RRC 回落 IDLE），因此**每个定位周期都会断开 MQTT → 扫描 → 重连 MQTT**（与本次受控实验完全同款的断开/重连代码路径）。

- 室内 LBS 场景（无 GNSS，每周期都走 WiFi 扫描 + MQTT 重连）：**约半天触发一次静默重启**，与现场多台设备表现一致
- 该问题已阻塞量产，且应用层无法绕过（destroy 已排除、client 已复用，泄漏仍在闭源 SDK 路径内）
